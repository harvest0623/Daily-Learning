# 为什么要分多agent
- 一个复杂任务可能在执行到一半的时候上下文就爆了，虽然可以采用压缩的手段，ClaudeCode的三层压缩策略也很优秀，但是压缩是有两面性的，压缩得太狠，会导致上下文信息丢失，压缩得太轻，又没办法回收上下文空间。所以，将任务拆分，让多个agent合作完成任务，每个agent负责完成任务的一部分，最后将结果合回主agent是一个很好的解决方案。

# 一个误区：子agent越多越好？
1. 多个Agent协同工作，上下文相互交织，排查问题的复杂度也翻倍
2. 协调本身就是开销：每多一个Agent，潜在的交互路径就会急剧增加

# 父子模式
一个父Agent生成一个子Agent，子Agent负责完成父Agent的任务的一部分，最后将结果合回父Agent。

- 如何委派任务给子Agent？
  1. 轻量委派：只描述任务，不包含任何上下文信息。 --- 父Agent自己也不知道任务答案，需要子Agent自己去搜索。
  2. 重量委派：除了描述任务，还附带一些上下文片段，帮助子Agent理解任务的上下文。 --- 父Agent知道任务的方向，需要子Agent去深挖结果。

- 子Agent完成任务后，结果怎么传回？
  1. claudeCode： 将子Agent的结果当成是一个工具结果，直接注入父Agent的上下文，如果子Agent的结果太长，那就截断，只保留必要的信息。---- 单向、同步、零延迟

  2. openClaw：打造了一个 Announce Queue机制，子Agent将结果存入通知队列，队列还增加了1s的防抖间隔（避免频繁打断父Agent）。---- 异步、并发高

# 多个Agent同时跑，怎么保证他们相互不干扰？
- 做一个上下文隔离机制，每个Agent都有自己的独立上下文。

    1. 共享内存，进程隔离：所有的Agent都在同一个进程，用语言层面的机制来隔离状态。
        claudeCode： Node.js 的 AsyncLocalStorage。创建一个 AsyncLocalStorage 实例，每个Agent都有自己的实例，互不干扰。 --- 没有额外的进程通信开销、启动快、内存压力小，但是隔离的不够狠，如果有某个Agent不小心修改了全局变量，其他Agent也会受到影响。

        OpenCode：将Agent的文件操作强行处理成同步，也就是同一时间只能有一个Agent在操作文件。不需要做隔离。 ---- 省掉了所有的并发控制操作，但是文件操作会变慢。

    2. Worktree，文件系统完全隔离
        - 如果子Agent需要做破坏性操作，比如删除文件、修改文件内容等

        claudeCode：给子Agent执行 git worktree。让每一个子Agent都有自己的工作目录，可以在自己的目录下做破坏性操作，改完后再合并到主目录。

    3. 用队列来串行化
        openClaw： 打造一个 Lane 机制，来保证同一个会话中的操作按顺序执行，天然不冲突。


# Swarm 模式
- 当需要多个子Agent合作完成任务，并且子Agent之间需要协调，才能完成任务时，就可以使用Swarm模式。
    1. 双向通信：需要一套消息传递机制，来保证子Agent之间的通信。（谁给谁发，怎么发，对方什么时候能收到）
    2. 共享状态：需要与一个共享的状态列表 --- 谁在做什么、做完了吗、还有哪些任务没有完成。
    3. 权限代理：子Agent遇到需要权限的操作，比如删除文件、修改文件内容等，把请求转发给父Agent，父Agent再问用户是否同意。

# MailBox：基于文件的消息传递机制
给每一个Agent配一个JSON文件来充当邮箱，要给其他Agent发送消息，就往其他Agent的邮箱文件里写入消息。Agent在轮Agent-Loop的时候，会检查自己的邮箱文件，如果有消息，就处理消息。

# 共享任务列表 ：怎么防止“抢活”？
文件锁 + 重试机制


# 权限代理
claudeCode：权限请求转发 --- 子Agent遇到需要权限的操作，就把这个请求写入到 pending 目录，父Agent会轮询这个目录，如果有请求，就问用户是否同意。用户如果拒接，父Agent会写入 resolved 目录，子Agent读取这个目录，来决定是否继续执行。
