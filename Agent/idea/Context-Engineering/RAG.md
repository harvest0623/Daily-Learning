# RAG 用处
1. 企业私域数据是没有被训练到模型中的，
2. Agent的记忆中也没有的数据

- 在模型生成回答之前，先去查资料，把相关的内容塞进上下文，让模型有据可依

- 开卷考试，翻书也可能找不到答案

- 数据质量决定了RAG的效果，而不是模型聪不聪明


# RAG 管线
1. 文档加载  （公司私域的数据读取）
2. 数据分块  （512 个 token 一个块）
3. Embedding  （把每块 token 转换为一个向量）
4. 向量储存 
5. 检索
6. 注入上下文

## 文档加载
1. Markdown 文档是最友好的格式
2. PDF 是最头疼的：
    用纯文本的方式读取 PDF 文档，但是会丢失很多信息
    - 简单的文本提取：pdf-parse ||  unpdf
    - 需要保留表格，标题等结构：pdfjs-dist  || Docling 

3. 代码文件 很特殊：代码不是文章，他有函数，有类，有模块等结构，把一个函数从中间切开会导致两个 chunk 都没意义

4. 网页数据要去噪：网页数据中包含了很多噪声，比如广告，导航栏， footer，需要先去掉噪声


- 数据的质量决定了RAG的上限


## 数据分块
1. 固定大小硬切
2. 递归分块：先按段落分，段落太长再按句子分，句子太长再按token分  （准确率最高）
3. 语义分块：用Embedding模型来判断相邻段落的语义相似度，把相似度高的段落放在一起

- 代码文件怎么切？
将代码处理成AST树，再按AST树的结构来切块
(一般代码已经不在处理成向量了，推荐claudeCode的方案 -- Glob、 Grep、 Read)

## Embedding 文字 -》 向量
- Embedding 模型是帮你算出来每个Chunk被处理成向量后，在多为空间中的坐标，用户查询的时候，提出的问题也会被处理成向量，然后和所有Chunk的向量进行相似度计算（最近的那个坐标），相似度最高的Chunk就是用户要找的

## 检索
- 语义相似不等于任务相关

- 混合检索（向量 + 关键词）


# Agentic RAG  把检索做成循环
  用户提问 -> Agent决定要不要搜 -> 搜到的内容够不够 -> 不够就换一个Query再搜 -> 或者掉一个工具来补充信息 -> 够了再生成回答



# 检索
  1. 向量检索： sqlite-vec 做余弦距离搜索
  2. 关键词检索： SQlite 做全文搜索

# Query改写
  - 用户的问题可能不适合直接做搜索

  - 在搜索前，先把用户的问题改写成更适合做检索的形式：
    HyDE：假设文档

    比如： 用户问 “上次部署除了什么问题”
    假设文档：将用户的问题改写，硬编一个问题出来 “上次部署Nginx配置没更新导致报错502”
