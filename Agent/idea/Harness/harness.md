# Harness
1. 模型不会自己停，它会在死循环里反复调用工具直到token耗尽。所以我们加了 max_turn 和 token预算作为 保险丝
2. 模型面对50+的工具数量，选择准确率会降到50%，所以我们做了 Deferred Loading 
3. 模型上下文退化，读到50个文件的时候前面的内容会遗忘，所以我们做了多级压缩策略
4. 模型不会记住你，每次对话都会从零开始，所以我们设计了 MEMORY.md 和 RAG检索系统
5. 模型一个人的上下文装不下，200个文件的仓库读到一半就走神，所以我们 Mulit-Agent把上下文拆开

    - 每个组件的背后，都是在假设模型做不到

    - Harness的本质：一组组件，每个组件对应一个模型的局限性假设，合在一起就构成了模型的运行环境。

    - Agent是一个基于Harness工程设计出来的AI产品


# 两个问题
1. 上下文退化：上下文焦虑 -- 模型主动偷懒：感知到上下文快满了，开始跳过步骤，简化回答，不调用工具。试图靠省着用 来维持上下文空间

2. 模型的自以为是：模型会用一些“合理化”来解释自己的决策，而这个决策得到的效果可能在我们的眼里是很差的 --- 最好的方案就是，不要让Generator自我评判，而是找一个独立的 Evaluator 来评判

# Generator/Evaluator：最经典的Harness模式

Generator：负责生成代码
Evaluator：负责评估代码的质量验收, 不看推理过程，只看最终的输出。
1. 用实际操作来验证代码的功能，而不是去读代码。
2. 先对齐验收标准，再开始干活 -- Sprint Contract 机制：先制定验收标准，而不是做完了再评估合不合格


# Harness会进化：模型越来越强，壳应该越来越薄

- Harness的进化：模型越来越强，就应该删除失效的假设，所以要补充新的组件来将模型的心得能力用起来

- 模型足够强，Harness会消失吗？
    - 不会，但是会分化为两层，其中一层确实会越来越薄弱
    1. 能力补偿：目前在做的一些组件就是补模型的能力，比如：Deferred Loading 是因为模型现在不能一次性在多个工具中准确选择。

    2. 系统工程：处理模型从定义上就做不了的事
