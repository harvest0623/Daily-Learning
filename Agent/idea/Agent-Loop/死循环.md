# 死循环、重复犯错、Token烧穿

假设你给Agent下了一指令，【把项目中的所有的console.log 替换成 logger.info】

- Agent出问题最常见的三种的方式：
    - 死循环： 反复调用同一个工具，做同样的事
    - Token烧穿：无限续写
    - 输出截断：模型输出到一半，被截断，它自己不知道


 ## 保险丝一：工具死循环检测
- OpenClaw设计了4种检测器来捕捉不同类型的死循环：
    1. 给每次工具调用打上“指纹”：SHA256(工具名 + （序列化）参数)

    2. 记录结果指纹： 同样的工具调用，同样的参数，同样的结果指纹才认为是无进展

- 4种检测器：
    1. 通用的重复检测：
        同一个工具调用，同样的参数，触发10次阈值，做警告，不阻断

    2. 无进展的轮训检测：
        不光看参数，还要看结果，如果状态长时间没有变化，Agent应该去干点别的

    3. Ping-Pong检测：
        两个工具的交替调用模式：
        read_file -> write_file -> read_file -> write_file -> ...

    4. 全局熔断
        上面三种情况都是无进展，只要累计30次无进展，强制停止，没有例外


 ## 保险丝二：Token预算控制
- 每次任务预算好Token，不能超过预算

    1. 90% 时，注入提示：
    “已完成Token目标的87%，（26170/30000）,继续工作---不要总结”

    2. 检测递减回报：
    续写第一次： +3000 Token  正常
    续写第二次： +2000 Token  正常
    续写第三次： +400 Token  增量很小
    续写第四次： +200 Token  连续两次递减，停止

  
 ## 保险丝三：输出截断恢复
- 模型输出到一半，被截断，它自己不知道

- 每个模型都有一个 max_output_tokens 参数，claude 默认是 8192个token，如果模型要说的话超过这个限制，就会被截断

claudeCode的处理方式：
1. 8k不够，提到64k
2. 注入恢复消息：
“输出Token限制被触发，直接从断电点继续--不要道歉，不要回顾你在做什么。如果是说到一半被截断了，从那个思路接着说，把剩下的工作拆成更小的块”
3. 认栽： 
    3次恢复都不行，那就把不完整的结果返回给用户，标记输出被截断
